## Architecture (unchanged in shape)

- **Public site** — static HTML, one stylesheet, two scripts, self-hosted fonts, no build step
  (`ennavizion/`). Kept deliberately: it's fast, cheap to host, and the academy's content
  needs don't justify a framework.
- **Backend** — Laravel 11 + Filament 3 admin (`backend/`). It's needed because enrolment
  data about children must be stored with access control, and payments need a server that
  holds the secret key. Everything else (league, programmes, settings) is managed there so
  staff never edit code.
- **Two hosting modes**, chosen automatically by hostname (`apiBase` in `js/data.js`):
  - `ennavizion.com` → uses `api.ennavizion.com`. Forms submit, donations can open, content
    comes from the admin panel.
  - anywhere else (today's Netlify site) → no backend. Forms are replaced by an email
    route; nothing pretends to send.

### League data model (new)

`league_seasons` (rules: points for win/draw/loss, ordered tie-breakers, which season is
current) · `league_season_team` · `league_teams` (name, is Ennavizion's) · `league_matches`
(one row per match — a fixture until it's played and scored; `is_published` is the approval
step). The table is never stored: `App\Services\LeagueStandings` calculates it from
published, played matches. Venues are a text field on the match rather than a separate
table — enough for one league; easy to split out later.

## Build and deploy

### Netlify (current site, static mode)

No build step. Publish directory: `ennavizion`. `_headers` in that folder sets the security
headers and caching; Netlify serves `404.html` for unknown paths automatically.

```powershell
npx netlify-cli@latest deploy --prod --dir ennavizion   # from the repo root, already linked
```

### Namecheap (planned: ennavizion.com + api.ennavizion.com)

Follow [DEPLOY.md](../DEPLOY.md). New since the original guide: the cron job for scheduled
tasks, backing up `APP_KEY`, the Paystack webhook URL, and the domain switch for the
sitemap/social tags.

### Backend environment variables

| Variable | Required | Purpose |
|---|---|---|
| `APP_KEY` | yes | Generated by `php artisan key:generate`. **Back it up** — it decrypts medical notes. |
| `APP_URL`, `FRONTEND_URL` | yes | API address; site address (CORS and the Paystack return page). |
| `DB_*` | yes | MySQL database from cPanel. |
| `MAIL_*`, `NOTIFY_EMAIL` | recommended | "New submission" emails (reference number only). |
| `PAYSTACK_MODE` | for contributions | `off` (default), `test` or `live`. Checkout opens only when mode and key agree; live must be set deliberately. |
| `PAYSTACK_SECRET_KEY`, `PAYSTACK_PUBLIC_KEY` | for contributions | `sk_test_` with `test`; `sk_live_` with `live` once authorised. |
| `SUBMISSION_RETENTION_DAYS` | academy decision | Blank = keep submissions until deleted by hand. |
| `CORS_EXTRA_ORIGINS` | optional | Extra site origins allowed to call the API. |

### Database

`php artisan migrate --force` applies three new migrations (submission references and
encrypted notes, optional programme fees, the league rebuild). The league migration moves
existing teams/fixtures/results into a season. It was run on the development database and
rolled back and re-applied cleanly on a copy. Take a database backup in cPanel before
migrating production.

## Contribution programme (business plan 2027)

- Options, purposes, allocations and 2027 goals live in `backend/config/contributions.php`
  (mirrored in `js/data.js` for the static site).
- Donors choose "where it is needed most" or a specific purpose; anything else is stored as
  restricted. Each donation records amount (naira and kobo), allocation, restricted flag and
  mode (test/live).
- Admin → Finance → **Contributions**: read-only list with search and filters, and totals of
  verified live payments only (pending, failed and test payments excluded; Paystack fees not
  deducted).
- Activation states: `off` shows the programme and an email route; `test` shows a working
  checkout with a "Test mode — no real money" banner; `live` only with `PAYSTACK_MODE=live`
  and an `sk_live_` key. Webhook signatures are still checked after checkout is switched off,
  so late confirmations are recorded.
- Not built yet: online **fee** payments for families. The plan describes them, but they need
  approved fees and an admission step (who is asked to pay what, and when). The Paystack
  layer is ready to reuse with a `type` of fee instead of donation.

## Security and privacy summary

- Admin panel: login required for every screen (tested); no public sign-up; accounts only
  created by an existing admin or on the server.
- Public API can read published content and create submissions — nothing else. Rate limits:
  submissions 10/min, donation start 5/min, verify 30/min per IP.
- Children's medical notes: encrypted with `APP_KEY`, stored apart from the rest of the
  application, shown only on the single-submission admin screen, never emailed.
- Notification emails and logs contain reference numbers and IDs, not personal details.
- Spam: hidden honeypot field + rate limits. No CAPTCHA (would add a third-party script).
- Paystack: secret key only on the server; our own reference; amount and currency checked;
  "paid" only from Paystack's verify API or a signed webhook; idempotent.
- Browser: strict Content-Security-Policy, no inline scripts, `X-Frame-Options: DENY`,
  HSTS, `nosniff`, restrictive Permissions-Policy (Netlify and Apache).
- The site no longer stores form data in the visitor's browser (and deletes what an older
  version left behind); the application draft lives only in that tab and excludes medical
  notes.

## Legal and safeguarding — decisions that need qualified review

These are flagged, not decided. Nothing on the site claims compliance.

- **Data protection.** The Nigeria Data Protection Act 2023 applies to the personal data the
  academy collects, including children's data and health information. A qualified adviser
  should confirm: the lawful basis and consent wording on the application form, the privacy
  policy text, the retention period, whether the academy must register with the Nigeria
  Data Protection Commission, and how access/deletion requests are handled.
- **Safeguarding.** The academy needs an approved safeguarding policy with a named lead,
  vetting procedure, code of conduct, and an escalation route to the relevant authorities.
  The site currently gives the national emergency number (112) and a way to raise a concern
  by email or the contact form.
- **Photos and video of children.** Consent process for publishing images (Gallery, news) and
  for the "filmed matches / scouting profile" ideas from the original site, which were
  removed until a consent process exists.
- **Enrolment terms** (fees, refunds, cancellations) before any fee is charged.

## Future enhancements (evaluated, not built)

Parent portal, coach dashboard, player development tracking, performance reports, scouting
access and attendance management all involve more personal data about children and
role-based access beyond "staff can see everything". Each needs its own requirements,
a data-protection impact assessment and role permissions in the admin (Filament supports
policies/roles). Recommended order once the basics are live: staff roles in the admin
(welfare lead vs coaches vs finance) → attendance → development reports shared with parents.

**Remaining issues**
- Home page LCP is 3.3 s in the throttled lab test (other pages 2.3–2.4 s). The LCP element
  is the hero photo, served from Unsplash. Replacing it with the academy's own photo, saved
  as WebP at 480/720/1000 px in `assets/images/`, removes the third-party connection.
- CSS and JS aren't minified (no build step by design). With compression on Netlify the
  saving would be small.
- The site renders content with JavaScript; without JS, pages show their static text but
  not programme lists, league data or forms.
- Illustrative stock photos remain until the academy supplies its own.
